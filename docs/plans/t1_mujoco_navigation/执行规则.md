# 所有步骤共同的执行与交接规则

## 1. 启动与范围

先读总规划、环境定位、执行看板、交接记录、本步任务和 records/Wxx.md，然后检查 `$WS` 的 Git 状态。只执行用户本次指定的 W 编号，不自动进入下一步，不启动子 agent。
文件名已经规定本步使用的配置；不要在本步内自行更换。任务能力不足时保存断点，由用户决定后续分派。
本步依赖未完成就记录 BLOCKED，说明缺少什么，不能用空实现让下游“先跑起来”。
源路径尚不存在与读取失败要区分，不能因权限拒绝推断文件为空。
重复进入同一步时，读取已有证据和 Git diff，从未完成项续做，禁止无理由从头重构。

## 2. 单一仓库的职责

`$WS` 是唯一项目仓库，存代码、配置、规划、执行记录、轻量证据、测试摘要、依赖锁定和开发说明。
`$PLAN` 是 `$WS/docs/plans/t1_mujoco_navigation` 的子目录，不是第二个仓库，不允许在其中创建嵌套 `.git`。
执行看板、交接记录和 `records/Wxx.md` 是执行状态的权威副本。规划文档与源代码同步版本化，任何 agent 都不能只改代码而不保存交接，也不能只改记录而不提交实现。

## 3. Git 操作

- 本规划迁入后，仓库已经有规划初始提交。W01 先审查并提交已验证的环境文档作为第二个基线提交，再创建 `feat/t1-mujoco-navigation` 分支；如果实际历史已变化，保持并记录，不重置。
- 后续步骤在该分支持续工作；用户串行交接，不必每步新分支。
- 使用 git status --short、git diff 和精确 git add 路径，禁止未审查的 git add .、force push、reset --hard、clean -fd。
- agent 开始本步时必须记录当前分支、HEAD 和 dirty 文件。完成一个可验证的子目标就做 checkpoint 提交；未通过全部测试的提交用 `wip(Wxx):` 前缀并明确失败项。WIP 可以恢复，不等于 DONE。
- 每步至少有一个实现/验证提交，采用单步文档给出的建议主题。实现提交后更新看板、交接和 `records/Wxx.md`，再以 `docs(Wxx): record completion and handoff` 提交记录。阶段完成后可打 `wxx-done` 轻量标签，标签存在时检查目标，不覆盖。
- 在记录中写完整代码 SHA，测试命令与测试所针对的 SHA；不能仅写“最新版本”。
- 记录文件引用本步实现提交的完整 SHA。记录提交本身不要求自引用；下一步从 `git log` 和看板读取最新记录提交。
- 保留原有 Git 作者配置；若没有作者身份，使用仓库局部的透明自动化身份 Codex <codex@local.invalid>，不伪造用户身份，不修改全局 Git 配置。
- 不 push、不建 PR、不删除用户文件。上游仓库保持原 SHA 和干净状态；必要适配写在自研包。必须修改上游时先写 ADR 和影响分析，不能默默破坏已验证基线。
- 忽略 build/install/log、venv、__pycache__、大 rosbag、视频与临时轨迹；追踪地图、配置、轻量 CSV 摘要、运行清单。策略与 mesh 记录 SHA/哈希/获取方式，不重复提交巨型资产。

## 4. 状态机

TODO（未完成）→ IN_PROGRESS（正在做）→ DONE（已完成）。
IN_PROGRESS 可转 BLOCKED（依赖阻塞）、PAUSED（会话中断）或 FAILED（验收失败）。
仅在产物存在、验收有证据、相关 Git 提交已完成、交接已更新后进入 DONE。
文档写完、构建成功、仿真窗口打开都不等于本步通过。

每个 agent 开始时立即填写执行看板的状态、时间和会话标识；同一时刻最多一行 IN_PROGRESS。
时间带时区，使用 Europe/Berlin 对应偏移或 UTC，不用模糊的“刚刚”。

## 5. 强制断点

每完成一个检查点、每次失败实验、每次重要参数变更立即保存记录；连续工作每 20–30 分钟至少更新一次。
若上下文/额度接近上限，优先花剩余预算保存工作，而不是启动新长实验。不能依赖系统在耗尽前一定发出提示。
记录格式见 records/交接模板.md。至少写：
当前状态、目标、已完成/正在做/未完成；分支和起始/最新 SHA；脏文件及用途；最近通过和失败的命令、退出码及证据路径；失败假设和已排除原因；下一条可直接执行的命令；运行进程 PID、工作目录、端口/ROS_DOMAIN_ID；可安全停止的方法。
大日志留在 $WS/docs/evidence/Wxx/raw 或被忽略的运行目录，交接只保留摘要、行号、路径，不把几万行日志复制进聊天。
暂停前让机器人进入已验证的停止状态，退出自己启动的进程或明确记录交接；不能 kill 全部 Python/ROS 进程。

## 6. 单步文档的使用

每个单步文件含检查点 C1–C4。records/Wxx.md 是检查点状态的权威文件；任务说明正文通常不改。
每步完成后在执行看板更新状态和实现 SHA，在交接记录写当前最近可复现状态，追加该步记录的实验与验收表，然后提交同一个项目仓库。
跨步骤改动写入决策记录并指出需要重测哪些已完成步骤；受影响证据失效时不能保留虚假的 DONE。

## 7. 验证和失败处理

统一记录命令、cwd、环境、退出码、开始/结束时间、结果、证据文件和运行版本。test PASS 和未运行必须清楚区分。
GUI 成功需要实际画面证据或用户亲眼确认；启动进程不证明窗口渲染正常。
运行实验时同时保存仿真时间和墙钟，禁止用墙钟速度误判物理速度。
同一错误最多两次无新证据的重复尝试。第三次先读日志、缩小故障、记录根因假设；不要升级所有依赖碰运气。
允许修复本步和依赖接口的小问题，但扩展训练/真机/换机器人/换仿真平台等需用户决策。

## 8. 最终汇报格式

向用户报告：本步状态；产物路径；通过/失败/未运行的验收；实现提交 SHA；交接记录提交 SHA；剩余问题；下一步 W 编号。
若阻塞，给出具体缺失输入和已经完成的独立工作，不写笼统的“环境有问题”。
